We will design it so that:

- A **Hub** is a playable map cluster.
- A **Quantum Warp** is a data-driven transition between hubs.
- A **Parallel Universe** is just higher-level metadata.
- A future **Galaxy Map / Starship Map** can be layered on top without breaking the foundation.
- Everything can be expanded bit by bit through OpenNefia-style mods and data prototypes.

# Quantum Effect — World & Hub Architecture Blueprint

## Design Goal

Create a scalable hub-zoning system for OpenNefia that supports:

```text
Parallel Universe
↓
Galaxy / Quantum Void
↓
System
↓
Earths / Planets
↓
Planet / Faction HQ
↓
Major City
↓
Area / Quantum Warp
↓
Architecture
```

But implement only the minimum living spine first:

```text
Hub Map A
↓
Warp Gate
↓
Warp Menu
↓
Hub Map B
```

This gives you a playable, expandable world system immediately.

---

# 1. Core Concept

We will treat the world as a **graph**.

## Nodes

Nodes are places the player can exist.

Examples:

```text
First Earth Slum
Quantum Lab Ruins
Aurelian Order Chapel
Technopunk Alley
Unknown Earth Outpost
Quantum Baby Memorial
```

Each node is a **Hub**.

## Edges

Edges are connections between hubs.

Examples:

```text
First Earth Slum → Quantum Lab Ruins
Quantum Lab Ruins → First Earth Slum
First Earth Slum → Technopunk Alley
Aurelian Chapel → Aurelian Inner Sanctum
```

Each edge is a **Warp Route**.

## Triggers

Triggers are how the player accesses warp routes.

Examples:

```text
Warp Gate
Quantum Rift
Elevator
Hidden Passage
Starship Boarding Terminal
```

In the first implementation, we use a **Warp Gate Feat**.

---

# 2. Scale Mapping

The full *Quantum Effect* scale is massive, but we can map it cleanly onto hub architecture.

| Quantum Effect Layer | OpenNefia Implementation | Initial Priority |
|---|---|---:|
| Parallel Universe | Data metadata / universe ID | Future |
| Galaxy / Quantum Void | Data metadata / future UI | Future |
| System | Data metadata / future UI | Future |
| Earths / Planets | Data metadata / hub cluster | Future |
| Planet / Faction HQ | Hub cluster | Medium |
| Major City | Hub map | High |
| Area / Quantum Warp | Warp route / zone transition | High |
| Architecture | Interior map | High |

For now, we only need to fully implement:

```text
Hub
Warp Route
Warp Gate
Map Transition
```

The larger cosmic layers can exist as metadata from day one, so future systems do not require painful refactoring.

## 4.3 Warp Gate Prototype

The Warp Gate is the physical object the player interacts with.

Example:

```lua

    _id = "qe.feat.warp_gate",
    _type = "base.feat",

    graphic = "QE_PROP_WARP_GATE_001",

        "qe_warp_gate",
    },

```

The exact interaction hook depends on how OpenNefia exposes feat interaction. We can implement it either through:

1. A built-in interact callback, if available.
2. A global event callback.
3. A custom QE interaction API.

The safest architecture is to keep the actual logic inside:

```text
qe_world/api/warp.lua
```

So the feat only says:

```text
Player interacted with a warp gate.
```

Then the Warp API decides what happens.

# 5. Runtime Flow

This is the full flow for a Quantum Warp.

```text
Player interacts with Warp Gate
↓
QE Warp API receives interaction
↓
Determine current Hub
↓
Find available Warp Routes from current Hub
↓
Filter locked routes
↓
Open Warp Menu UI Layer
↓
Player selects destination
↓
UI returns selected route
↓
Apply warp cost / effects
↓
Trigger warp feedback
↓
Transition player to destination Hub Map
↓
Update discovered hubs / save data
↓
Emit warp completion event
```

# 6. API Design

We want the actual logic to be cleanly reusable.

---

## 6.1 `api/world.lua`

This module answers world queries.

Planned functions:

```lua
World.get_hub(hub_id)
World.get_hub_by_map(map)
World.get_routes_from_hub(hub_id)
World.is_route_available(route_id)
World.discover_hub(hub_id)
World.is_hub_discovered(hub_id)
World.get_current_hub(chara)
```

Example pseudo-implementation:

```lua
local World = {}

function World.get_hub(hub_id)
    return data["qe.world.hub"][hub_id]
end

function World.get_routes_from_hub(hub_id)
    local routes = {}

    for _, route in pairs(data["qe.world.warp_route"]) do
        if route.from_hub == hub_id then
            table.insert(routes, route)
        end
    end

    return routes
end

function World.is_hub_discovered(hub_id)
    local save = Save.get_qe_world_save()

    if save.discovered_hubs[hub_id] then
        return true
    end

    local hub = World.get_hub(hub_id)

    return hub.discovered_by_default
end

function World.discover_hub(hub_id)
    local save = Save.get_qe_world_save()
    save.discovered_hubs[hub_id] = true
end

return World
```

---

## 6.2 `api/warp.lua`

This module handles Quantum Warp behavior.

Planned functions:

```lua
Warp.interact_with_gate(chara, feat)
Warp.open_warp_menu(chara, hub)
Warp.execute_route(chara, route)
Warp.apply_cost(chara, route)
Warp.apply_instability(chara, route)
Warp.can_use_route(chara, route)
```

Example pseudo-implementation:

```lua
local Warp = {}

function Warp.interact_with_gate(chara, feat)
    local hub = World.get_current_hub(chara)

    if not hub then
        -- Fallback message: unstable location
        return
    end

    local routes = World.get_routes_from_hub(hub._id)

    if #routes == 0 then
        -- Message: The gate has no destination.
        return
    end

    local selected_route = Warp.open_warp_menu(chara, routes)

    if selected_route then
        Warp.execute_route(chara, selected_route)
    end
end

function Warp.execute_route(chara, route)
    if not Warp.can_use_route(chara, route) then
        return
    end

    Warp.apply_cost(chara, route)
    Warp.apply_instability(chara, route)

    local destination_hub = World.get_hub(route.to_hub)

    World.discover_hub(destination_hub._id)

    -- Transition to destination map here.

    Event.trigger("qe.event.warp_completed", chara, route)
end

return Warp
```

# 8. Map Transition Design

This is the most technically important part.

We need a safe way to say:

```text
Move this character from current hub map to destination hub map.
```

We should wrap this in an API:

```text
api/hub_map.lua
```

Planned functions:

```lua
HubMap.load_hub_map(hub_id)
HubMap.transfer_chara_to_hub(chara, hub_id)
HubMap.place_chara_at_entry(chara, hub)
HubMap.register_map_hub_relationship(map, hub_id)
```

Conceptual flow:

```lua
function HubMap.transfer_chara_to_hub(chara, hub_id)
    local hub = World.get_hub(hub_id)

    if not hub then
        error("Unknown QE hub: " .. tostring(hub_id))
    end

    local destination_map = HubMap.load_hub_map(hub)

    -- Remove chara from current map
    -- Insert chara into destination map
    -- Place at hub.entry_position
    -- Set player camera/focus if necessary
    -- Save current hub and last position
end
```

We should not scatter map transition code across many mods. All transitions should go through this API.

# 9. Save Data Design

Because this is a growing project, save data must be planned carefully.

We will store QE world state inside a dedicated save namespace.

Example:

```lua
save.qe_world = {
    current_universe = "qe.universe.first_earth_branch",
    current_hub = "qe.hub.first_earth_slum",

    discovered_hubs = {
        ["qe.hub.first_earth_slum"] = true,
    },

    unlocked_routes = {
        ["qe.warp_route.first_earth_slum_to_quantum_lab"] = true,
    },

    last_location = {
        hub_id = "qe.hub.first_earth_slum",
        x = 12,
        y = 18,
    },

    warp_count = 0,
    quantum_instability = 0,
}
```

This lets us support:

- Returning to previous locations.
- Fast travel later.
- Story unlocks.
- Faction unlocks.
- Parallel universe tracking.
- Quantum instability effects.
- Save-safe hub discovery.

# 15. Acceptance Criteria

Option B is complete when the following are true.

## Functional criteria

```text
1. Player can stand in First Earth Slum.
2. Player can interact with a Warp Gate.
3. A Warp Menu appears.
4. The menu shows Quantum Lab Ruins.
5. Selecting it transitions the player to Quantum Lab Ruins.
6. Player can use a Warp Gate in Quantum Lab Ruins to return.
7. Save/load preserves discovered hubs.
8. Save/load preserves current hub.
9. Adding a new hub requires mostly data entry.
10. Adding a new route requires mostly data entry.
```

## Architectural criteria

```text
1. No hub-specific logic is hardcoded into the map.
2. Warp routes are data-driven.
3. UI does not directly modify world state.
4. Transition logic is centralized.
5. Save data is namespaced under qe_world.
6. Future systems can listen to warp events.
```
