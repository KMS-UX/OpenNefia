> **Option A: The Quantum Baby Schema**

This blueprint is designed to be:

- Feasibility-first.
- OpenNefia-native.
- Mod-friendly.
- AI-assistant-friendly.
- Expandable over time.
- Safe for continuous development.

---

# 1. Locked Defaults for Option A

## Core Resources

We will use four protagonist resources:

```text
Quantum Energy
Humanity
Original Sin
Sync Rate
```

## Starting Values

Recommended starting values:

| Resource | Start | Min | Max |
|---|---:|---:|---:|
| Quantum Energy | 10 | 0 | 50 |
| Humanity | 100 | 0 | 100 |
| Original Sin | 0 | 0 | 100 |
| Sync Rate | 25 | 0 | 100 |

These are placeholder values, but they are good enough for system testing.

---

## Augmentation Slots

We will use four slots:

```text
Neuro
Limbs
Torso
Spinal
```

Starting slot states:

| Slot | Starting State |
|---|---|
| Neuro | Unlocked |
| Limbs | Unlocked |
| Torso | Locked |
| Spinal | Unlocked |

Each slot initially supports:

```text
1 installed augment
```

Slot capacity can be expanded later.

---

## Test Augmentations

We will create three placeholder augments:

```text
Basic Neuro Chip
Limb Servo
Spinal Reflex Booster
```

Their purpose is not balance. Their purpose is to prove that:

- Slots work.
- Installation works.
- Removal works.
- Resource costs work.
- Modifiers work.
- Save/load persistence works.

---

## Player Creation

For Option A, we will not build a full character creator.

Instead:

```text
The player is treated as a Quantum Baby by initializing QE state on the player character.
```

This can happen through:

- A new-game initialization event.
- A save-load initialization event.
- A debug command.

This keeps the first implementation small.

---

## UI

No final UI yet.

We will use:

```text
Debug commands
Log output
Test assertions
```

A proper Quantum Baby status screen can come later.

# 2. Option A Definition of Done

Option A is complete when:

1. A `qe_core` mod loads inside OpenNefia.
2. The Quantum Baby state can be initialized.
3. The four resources can be read and modified safely.
4. The four augmentation slots exist.
5. Three test augments can be installed and removed.
6. Installing an augment applies effects.
7. Removing an augment removes reversible effects.
8. Original Sin gains are permanent by default.
9. The state survives save/load.
10. Debug commands can inspect and modify the state.
11. The schema is documented.

```text
qe_core.resource
```

The exact OpenNefia data registration syntax must be validated against the actual codebase, but the conceptual schema should look like this.

## 5.1 `qe_core.resource`

Purpose:

Defines a Quantum Effect resource type.

Fields:

```text
id
name
description
min
max
default_value
default_max
can_exceed_max
regen_per_turn
ui_color
tags
```

Example:

```lua
{
    type = "qe_core.resource",
    id = "qe_core.resource.quantum_energy",
    name = "Quantum Energy",
    description = "Energy used to fuel Quantum Effects and augmented abilities.",
    min = 0,
    max = 50,
    default_value = 10,
    default_max = 50,
    can_exceed_max = false,
    regen_per_turn = 0,
    ui_color = { r = 80, g = 180, b = 255 },
    tags = { "quantum", "energy" },
}
```

We will define four resources:

```text
qe_core.resource.quantum_energy
qe_core.resource.humanity
qe_core.resource.original_sin
qe_core.resource.sync_rate
```

# 7. Abstract Stat Modifiers

To avoid depending too early on unknown Elona/OpenNefia stat fields, we should first use abstract QE modifier targets.

Recommended abstract targets:

```text
qe.stat.neural_amp
qe.stat.physical_amp
qe.stat.reflex_amp
qe.stat.action_efficiency
qe.stat.quantum_amp
```

Later, we can map these to actual OpenNefia stats once we inspect the character/stat system.

Example:

```text
qe.stat.neural_amp
  → intelligence, mental stat, or skill-related bonus

qe.stat.physical_amp
  → strength, physical power, or melee capability

qe.stat.reflex_amp
  → speed, evasion, or action timing

qe.stat.action_efficiency
  → turn cost reduction or action speed
```

For Option A, it is acceptable if these only exist inside QE state at first. The important part is that the modifier pipeline works.

# 8. Quantum Baby Save State Schema

We need a save-safe state object.

Use versioning from day one.

```text
QE_CORE_SAVE_VERSION = 1
```

---

## Proposed State Shape

```lua
{
    version = 1,

    archetype = "qe_core.chara.quantum_baby",

    resources = {
        current = {
            ["qe_core.resource.quantum_energy"] = 10,
            ["qe_core.resource.humanity"] = 100,
            ["qe_core.resource.original_sin"] = 0,
            ["qe_core.resource.sync_rate"] = 25,
        },

        max = {
            ["qe_core.resource.quantum_energy"] = 50,
            ["qe_core.resource.humanity"] = 100,
            ["qe_core.resource.original_sin"] = 100,
            ["qe_core.resource.sync_rate"] = 100,
        },

        base_max = {
            ["qe_core.resource.quantum_energy"] = 50,
            ["qe_core.resource.humanity"] = 100,
            ["qe_core.resource.original_sin"] = 100,
            ["qe_core.resource.sync_rate"] = 100,
        },
    },

    slots = {
        unlocked = {
            ["qe_core.augment_slot.neuro"] = true,
            ["qe_core.augment_slot.limbs"] = true,
            ["qe_core.augment_slot.torso"] = false,
            ["qe_core.augment_slot.spinal"] = true,
        },

        installed = {
            ["qe_core.augment_slot.neuro"] = nil,
            ["qe_core.augment_slot.limbs"] = nil,
            ["qe_core.augment_slot.torso"] = nil,
            ["qe_core.augment_slot.spinal"] = nil,
        },
    },

    permanent = {
        humanity_max_loss = 0,
        original_sin_gained = 0,
    },

    flags = {},

    history = {
        installed_augments = {},
        uninstalled_augments = {},
        resource_changes = {},
    },
}
```

We can decide during Milestone 1 whether this state should be stored:

1. On the player character object.
2. In mod-level save data.
3. In both, with the mod-level save as the source of truth.

For feasibility, mod-level save data keyed to the player is safest.

# 9. Public API Design

The public API should be split into focused modules.

---

## 9.1 `QE.Core`

Purpose:

Versioning, save state access, initialization, migration.

Functions:

```text
QE.Core.get_version()
QE.Core.get_save_data()
QE.Core.ensure_save_data()
QE.Core.migrate_save_data(save_data)
QE.Core.get_player_state()
QE.Core.initialize_player_state(chara)
```

---

## 9.2 `QE.QuantumBaby`

Purpose:

Protagonist-specific helpers.

Functions:

```text
QE.QuantumBaby.is_quantum_baby(chara)
QE.QuantumBaby.mark_as_quantum_baby(chara)
QE.QuantumBaby.get_state(chara)
QE.QuantumBaby.ensure_state(chara)
QE.QuantumBaby.get_flag(chara, key)
QE.QuantumBaby.set_flag(chara, key, value)
```

---

## 9.3 `QE.Resources`

Purpose:

Safe resource modification.

Functions:

```text
QE.Resources.get(chara, resource_id)
QE.Resources.get_max(chara, resource_id)
QE.Resources.get_base_max(chara, resource_id)

QE.Resources.set(chara, resource_id, value)
QE.Resources.set_max(chara, resource_id, value)

QE.Resources.add(chara, resource_id, amount)
QE.Resources.spend(chara, resource_id, amount)
QE.Resources.can_spend(chara, resource_id, amount)

QE.Resources.modify_max(chara, resource_id, amount)
QE.Resources.recalculate_max(chara)
```

Rules:

```text
Values are clamped between min and max.
Max values are recalculated from base_max + modifiers.
Resource changes emit events.
```

---

## 9.4 `QE.Augments`

Purpose:

Augmentation slot and installation logic.

Functions:

```text
QE.Augments.get_slot_state(chara, slot_id)
QE.Augments.is_slot_unlocked(chara, slot_id)
QE.Augments.unlock_slot(chara, slot_id)
QE.Augments.lock_slot(chara, slot_id)

QE.Augments.get_installed(chara, slot_id)
QE.Augments.get_all_installed(chara)

QE.Augments.can_install(chara, augment_id)
QE.Augments.install(chara, augment_id)
QE.Augments.uninstall(chara, slot_id)

QE.Augments.recalculate_modifiers(chara)
```

---

## 9.5 `QE.Events`

Purpose:

Central event naming and emission.

Functions:

```text
QE.Events.emit(name, payload)
QE.Events.register(name, callback, priority)
```

This gives future mods a stable hook surface.

---

## 9.6 `QE.Debug`

Testing and inspection commands.

Functions:

```text
QE.Debug.print_state(chara)
```

# 10. Event Design

We need two kinds of events:

1. OpenNefia engine events.
2. QE custom events.

The exact engine event names must be validated in Milestone 1.

---

## 10.1 Engine Events to Investigate

We should look for events similar to:

```text
After save data initialization
After save load
After player character creation
Before/after character stat calculation
Before/after turn action
On mod startup
```

In OpenNefia’s architecture, event callbacks are the main way to extend logic, so this is the correct place to hook.

---

## 10.2 QE Custom Events

These are stable event names exposed by `qe_core`.

```text
qe_core.initialized

```

Future systems can subscribe to these without editing core logic.

# 11. Modifier Pipeline

We should avoid directly mutating base stats whenever possible.

Instead:

```text
Installed Augments
↓
Collect Modifier List
↓
Apply Modifier Pipeline
↓
Update QE Modifier Cache
↓
Emit qe_core.modifiers.recalculated
↓
Optional: Hook into OpenNefia stat/action events
```

---

## Modifier Object Shape

```lua
{
    source = "qe_core.augment.neuro_basic",
    target = "qe.stat.neural_amp",
    mode = "add",
    value = 1,
}
```

Supported modes initially:

```text
add
multiply
```

We may later add:

```text
set
clamp
base_add
final_add
```

But for Option A, keep it simple.
